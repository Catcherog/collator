# ADR-001: collator V1 核心架构与边界决策

## Status

Accepted

## Context

collator 是泽怀影像工作室的非结构化数据结构化摄入 Agent，需要在 Trae IDE 中实现端到端数据自动化：接收任意渠道的原始数据（聊天记录、OCR 结果、语音转写、文档附件等），自动解析、清洗、标准化后写入飞书多维表。

V1 阶段需要在有限交付窗口内完成核心闭环，同时复用已有的 Node.js 清洗/校验/Schema 资产（`src/data-cleaning`）。在启动 Phase 1 前，需要明确技术栈、职责边界、安全边界与审核策略，避免范围蔓延和架构反复。

详细决策历史（ADR-001 ~ ADR-010）见 `docs/DECISIONS.md`。本 ADR 仅汇总影响跨 Phase 的最关键架构决策。

## Decision

以下三条决策构成 V1 核心架构基石：

### 1. 技术栈与资产复用策略（对应 docs/DECISIONS.md ADR-003）

采用 TypeScript + Fastify + Node.js 20+ 作为 V1 Core Service 技术栈。保留现有 `src/data-cleaning` Node.js 清洗/校验/Schema 资产，通过 LegacyModuleLoader + Adapter 边界增量改造而非整体重写。V1 不使用 LangChain/LangGraph/ReAct Agent（ADR-002）。

### 2. Dify 与 Collator Core 的职责边界（对应 docs/DECISIONS.md ADR-004）

Dify 只负责语义提取与外层工作流，不直接写飞书业务主表，不维护状态机/幂等/回滚。Collator Core 负责确定性清洗、五重校验、幂等、查重、审核状态与飞书写入。飞书作为任务状态和业务事实中心（ADR-006），生产用 `FeishuTaskRepository`，测试用 `InMemoryTaskRepository`。

### 3. 安全与审核边界（对应 docs/DECISIONS.md ADR-005、ADR-007、ADR-009、ADR-010）

- V1 全人工审核，`AUTO_COMMIT_ENABLED=false`（ADR-005）。
- 生产数据隐私边界：Dify Cloud 只用合成/脱敏数据；.env/Token/Secret 不入 Git（ADR-007）。
- Callback 使用 HMAC + 时间戳验签，拒绝超时与重放（ADR-009）。
- 手机号等敏感信息日志脱敏，原始聊天不进入普通应用日志（ADR-010）。

## Consequences

- **正向**：技术栈现代化且复用 Legacy 资产，降低重写风险；职责清晰分离 Dify 与 Core；安全边界明确，便于 Gate E 验收。
- **负向**：Legacy 资产通过 Adapter 边界接入，引入 `src/server/cleaning` 复杂度；中英文字段映射层需在 Phase 2 补齐（DEBT-004）；`core/data-cleaner.js` 的 import-time 副作用需逐步抽取纯函数（DEBT-006）。
- **范围约束**：V1 只支持 `customer_consultation` 纯文本链路（ADR-008），只写客户主表；其他业务场景延后。

## Revisit When

- 单实例处理能力成为实际瓶颈时，重新评估同步处理与消息队列（见改造方案第 15 节示例）。
- 需要支持多业务场景（订单/拍摄/模特等）时，重新评估 Schema 与字段映射层抽象。
- Legacy `src/data-cleaning` 完成迁移清理后（Phase 3+），重新评估是否保留 Adapter 边界。
