## 第一章 执行摘要

### 1.1 规划背景

泽怀影像工作室业务规模持续扩张，已形成涵盖客户咨询、订单管理、拍摄执行、模特资源、客户主表、话术库、异常日志的 7 张核心多维表数据体系。然而，伴随业务沉淀的大量非结构化数据（SOP 文档、合同、策划案、客户沟通记录、拍摄素材、模特资料、会议纪要等）散落于飞书知识库（31 节点）、云盘（130 项）与本地文档集中，存在命名不规范、分类混乱、关联缺失、维护单点风险等问题，导致 collator Agent 数据摄入效率受限、业务资产检索耗时偏长、跨表追溯链路不畅。本规划旨在系统化建立非结构化数据与核心多维表的映射体系，为业务决策与 AI 数据治理提供可追溯、可检索、可维护的数据底座。

### 1.2 核心目标

1. **建立统一的非结构化数据分类体系**：覆盖 6 大类数据，配套标准命名规范与 23 项必备元数据字段。
2. **重构知识库与云盘目标结构**：知识库形成 7 个一级节点、≤3 层的目标分类树；云盘完成根目录清理与空文件夹填充。
3. **建立非结构化数据与 7 张核心多维表的双向映射**：通过 STRONG/WEAK 关联方式，实现文件级业务追溯。
4. **构建自动化治理工具链**：5 类工具 19 人天工作量，支撑扫描、重命名、元数据提取、映射校验全流程。
5. **建立常态化维护机制**：24 小时变更更新、周度/月度校验、P0/P1/P2 三级 SLA 异常处理闭环。

### 1.3 关键发现（Phase 1 现状调研）

1. **知识库结构整体良好但局部失序**：31 个节点中 5 个命名不规范、4 处分类混乱、3 组内容重复、4 个僵尸/占位节点；"五、数据与复盘"分类形同虚设。
2. **云盘业务关联率 85.5%，孤立率 14.5%**：9 个孤立文件（含 6 份会议纪要、空名称文档、热点.docx 等）无法关联核心表；30 个作品文件夹仅扫描 1 个，深层目录覆盖率仅 7.7%。
3. **核心表关联分布不均**：拍摄执行表关联 44 文件（最重）、客户信息主表 30、模特信息表 7、订单管理表 6、客户咨询表 3；话术库与异常日志表与云盘无关联（设计如此）。
4. **3 项核心 SOP 缺失**：订单管理 SOP、客户主表维护 SOP、异常处理 SOP 尚未文档化，影响业务标准化。
5. **单点维护风险突出**：知识库 31 节点全部由同一所有者维护；云盘根目录 Token 已失效一次（原 `K9QEfQJCkli462dHDLxcP5K9n7d` 被删除），需建立 Token 治理机制。

## 第三章 映射规则设计

### 3.1 非结构化数据分类体系

#### 3.1.1 6 大类数据清单

| 数据大类 | 类型前缀 | 典型格式 | 来源渠道 | 业务用途 |
|---------|---------|---------|---------|---------|
| **业务文档类** | SOP/CONTRACT/QUOTE/PLAN/TPL | .docx .pdf .sheet .slides | 知识库、云盘项目归档库、文件模板库 | 标准化作业、合同签订、报价参考、策划、岗位权责 |
| **客户沟通类** | CHAT/VOICE | .png .jpg .mp3 .m4a .docx .json | 微信/小红书/抖音聊天、飞书妙记 | 客户需求分析、报价依据、纠纷追溯、话术优化 |
| **拍摄素材类** | PHOTO/BTS/VIDEO/RAW | .jpg .png .mp4 .mov .raw | 拍摄现场、后期修图、客户交付 | 成品交付、平台分发、作品集展示、复盘 |
| **模特资料类** | MODEL/RESUME/RES | .jpg .mp4 .docx .pdf .sheet | 小红书招募、模特自荐、机构推荐 | 模特筛选、匹配推荐、合作记录、资源库维护 |
| **配置文件类** | CONFIG | .json .env .md .ps1 .sh | collator 项目、飞书 API 配置 | 系统初始化、API 认证、字段映射、数据摄入 |
| **其他类** | MEETING/TRAIN/KNOW | .docx .pdf .mindnote | 飞书会议、内部培训、外部引进 | 决策追溯、团队培训、知识沉淀、年度规划 |

#### 3.1.2 标准命名规范

**通用命名公式**：

```
{类型前缀}_{业务ID}_{日期YYYYMMDD}_{版本}.{扩展名}
```

| 组成部分 | 取值规范 | 说明 |
|---------|---------|------|
| 类型前缀 | 大写英文（见上表） | 标识数据类型，便于排序与检索 |
| 业务ID | 客户ID/订单号/模特ID/拍摄主题编号 | 强关联核心表主键；无业务ID时用 `COMMON` |
| 日期 | YYYYMMDD（8位） | 文件创建或业务发生日期 |
| 版本 | v1/v2/v3... 或 draft/final | draft=草稿，final=定稿；定稿后修改需重新进入 draft |
| 扩展名 | 小写 | 统一小写，避免 .JPG/.jpg 混用 |

**命名示例**：

| 数据类型 | 命名示例 |
|---------|---------|
| SOP 文档 | `SOP_SHOOT_20260427_v2.docx` |
| 合同 | `CONTRACT_ORD20260618001_20260618_final.docx` |
| 报价单 | `QUOTE_CUST202601_20260618_v1.docx` |
| 策划案 | `PLAN_28_夏合情思_20260614_final.docx` |
| 客户沟通截图 | `CHAT_CUST202601_WX_20260618_v1.png` |
| 语音转写 | `VOICE_CUST202601_20260618_final.docx` |
| 成品照片 | `PHOTO_28_夏合情思_001_20260614_final.jpg` |
| 花絮视频 | `BTS_28_夏合情思_20260614_final.mp4` |
| 模特模卡 | `MODEL_MD001_20260618_v1.jpg` |
| 配置文件 | `CONFIG_lark-cli_20260618_v1.json` |
| 会议纪要 | `MEETING_业务规划_20260311_final.docx` |

**命名约束**：
1. 禁止字符：`/ \ : * ? " < > |` 及中文标点 `【】（）`；占位标记必须在定稿前清除。
2. 分隔符：组成部分之间用下划线 `_`，业务ID内部用连字符 `-`。
3. 中文使用：业务ID中的拍摄主题、客户名可保留中文，前缀和日期必须为 ASCII。
4. 版本升级：`draft` → `v1` → `v2`；`final` 后如再修改需重新进入 `draft` 流程。

#### 3.1.3 必备元数据字段（23 字段矩阵）

| 字段类别 | 字段名 | 类型 | 是否必备 | 说明 |
|---------|--------|------|---------|------|
| **业务关联** | customer_id | string | 条件必备 | 客户ID，客户相关数据必备 |
| **业务关联** | order_id | string | 条件必备 | 订单号，订单/合同/拍摄相关必备 |

### 3.5 与核心多维表关联规则

#### 3.5.1 关联方式定义

| 关联方式 | 定义 | 触发条件 | 示例 |
|---------|------|---------|------|
| **STRONG（强关联）** | 数据直接依赖核心表记录存在，删除记录则数据失效 | 文件元数据包含对应核心表的主键字段且非空 | 合同↔订单管理表（order_id 非空） |
| **WEAK（弱关联）** | 数据与核心表有业务关联，但不依赖记录存在 | 文件元数据包含业务标识但无主键，或通过目录结构推断 | 资源表↔拍摄执行表（通过资源类型推断） |

#### 3.5.2 各核心表关联规则

| 核心表 | 主键字段 | 关联元数据字段 | 关联方式 | 关联场景 |
|--------|---------|--------------|---------|---------|
| 客户咨询表 | 咨询记录ID/customer_id | customer_id, business_scene=ACQ | STRONG（客户沟通类）/ WEAK（话术库） | 客户咨询记录、聊天截图、语音转写、话术引用 |
| 订单管理表 | order_id | order_id, customer_id | STRONG（合同/报价单/项目统计） | 合同、报价单、项目统计表、成品发布情况表 |
| 拍摄执行表 | 拍摄任务ID/shoot_theme | shoot_theme, shoot_date, order_id | STRONG（策划案/成品/花絮/短视频）/ WEAK（资源表） | 策划案、成品照片、花絮视频、短视频、底片、场地/化妆/道具资源表 |
| 模特信息表 | model_id | model_id | STRONG（模特模卡/简历/模特资源表） | 模特模卡、模特简历、模特资源表、服化道资源list |
| 客户信息主表 | customer_id | customer_id | STRONG（客户相关作品/沟通）/ WEAK（客户咨询记录） | 作品文件夹（含客户标识）、客户沟通记录、客户资源库 |
| 话术库 | 话术ID | business_scene=ACQ | STRONG（话术库节点） | 全场景话术库知识库节点 |
| 异常日志表 | 异常ID | integrity_status, related_table | WEAK（所有数据异常时记录） | 命名违规、关联缺失、完整性不足等异常 |

#### 3.5.3 collator Agent 自动识别关联流程（6 步）

```
非结构化数据输入
   ↓
Step 1: 文件名解析
   ↓ 提取类型前缀 + 业务ID + 日期 + 版本
   ↓
Step 2: 业务ID类型判断
   ├─ customer_id (CUST*) → 候选关联：客户咨询表/客户信息主表
   ├─ order_id (ORD*) → 候选关联：订单管理表
   ├─ model_id (MD*) → 候选关联：模特信息表
   ├─ shoot_theme (数字_名称) → 候选关联：拍摄执行表
   └─ COMMON → 候选关联：异常日志表（WEAK）
   ↓
Step 3: 元数据补全
   ↓ 调用 lark-base 查询候选表，验证业务ID是否存在
   ↓
Step 4: 关联确认
   ├─ 业务ID存在 → STRONG 关联，写入 related_record_id
   ├─ 业务ID不存在但目录/标签匹配 → WEAK 关联，记录推断依据
   └─ 完全无匹配 → 标记 integrity_status=MISSING，写入异常日志表
   ↓
Step 5: 双向关联建立
   ↓ 在核心表记录中更新"云盘文件链接"字段（需先在7张表新增此字段）
   ↓ 在文件元数据JSON中记录 related_table + related_record_id
   ↓
Step 6: 输出关联摘要
   → "已建立 STRONG 关联：PHOTO_28_夏合情思_001 ↔ 拍摄执行表 recXXX"
```

#### 3.5.4 核心表字段补全建议

为实现双向关联，建议在 7 张核心多维表中统一新增以下字段：

| 字段名 | 类型 | 说明 |
|--------|------|------|
| 云盘文件链接 | URL | 关联云盘文件的飞书链接（多选） |
| 知识库节点链接 | URL | 关联知识库节点的飞书链接（多选） |
| 文件数量 | 数字 | 关联文件总数（自动统计） |
| 最后更新时间 | 日期 | 关联文件最后修改时间 |

### 4.2 格式转换环节

| 维度 | 内容 |
|------|------|
| **输入条件** | 筛选环节输出的分类数据清单 + 原始文件 |
| **操作动作** | ① 文档统一转 docx/pdf；② 图片统一 jpg/png，分辨率规范；③ 音视频转码（H.264/AAC） |

| **验收标准** | 格式转换成功率 ≥ 98%；图片分辨率符合规范；音视频可正常播放 |

**格式转换规范**：

| 数据类型 | 输入格式 | 目标格式 | 转换工具 | 规范要求 |
|---------|---------|---------|---------|---------|
| 业务文档 | .doc/.docx/.wps/.txt | .docx（编辑用）/ .pdf（归档用） | 飞书云文档导入 / LibreOffice | 保留样式；PDF 用于定稿归档 |
| 业务文档 | .xlsx/.csv | .sheet（飞书电子表格） | 飞书云文档导入 | 保留公式与格式 |

**转换约束**：
1. 原文件保留：所有转换均保留原文件，转换后文件以 `_converted` 后缀区分，归档至"原文件备份"子目录。

## 第五章 数据更新与维护机制

### 5.1 时效性校验

#### 5.1.1 变更检测方式

| 检测方式 | 触发频率 | 检测范围 | 实现方式 |
|---------|---------|---------|---------|
| **定期扫描** | 每日 02:00（凌晨） | 全量云盘 + 知识库 | collator Agent 调用 lark-drive files list + lark-wiki nodes list，与昨日快照对比 |
| **事件触发** | 实时 | 单文件/节点 | 监听飞书云盘/知识库变更事件（webhook），触发增量更新 |
| **手动触发** | 按需 | 指定范围 | 用户通过 collator Agent 命令 `scan --path xxx --since yyyy-mm-dd` 触发 |

#### 5.1.2 24 小时内更新映射关系流程

```
T+0: 变更发生（文件新增/修改/删除/移动）
   ↓
T+1h: 变更检测（定期扫描或事件触发）
   ↓
T+2h: 进入 4.1 筛选环节（增量数据）
   ↓
T+6h: 完成 4.2-4.4 转换/提取/存储
   ↓
T+8h: 元数据 JSON 更新 + 核心表关联更新
   ↓
T+24h: 校验完成，输出变更日志
   ↓
若校验失败 → 写入异常日志表，进入 5.4 异常处理流程
```

#### 5.1.3 变更日志字段

每条变更日志记录以下字段，存入"异常日志表"或独立"变更日志表"：change_id, change_type（CREATE/UPDATE/DELETE/MOVE/RENAME）, file_name, file_path, affected_tables, affected_records, impact_scope（SINGLE/MULTIPLE/GLOBAL）, process_status（PENDING/PROCESSING/DONE/FAILED）, processor, process_time, change_time, remark。

### 5.2 准确性校验

#### 5.2.1 周度校验（每周一 06:00 执行，4 项）

| 校验项 | 校验方法 | 通过标准 | 异常处理 |
|--------|---------|---------|---------|
| 孤立文件检测 | 扫描云盘+知识库，识别无业务关联的文件 | 孤立率 ≤ 5% | 标记 MISSING，通知云盘管理员 |
| 命名规范检查 | 正则匹配文件名是否符合 3.1.2 节规范 | 规范符合率 ≥ 95% | 标记 NEEDS_RENAME，通知所有者 |
| 空文件夹检测 | 扫描云盘空文件夹 | 空文件夹数 = 0 | 通知云盘管理员决定填充或删除 |
| 存储位置一致性 | 检查文件实际路径与元数据 storage_path 是否一致 | 一致率 = 100% | 标记 PATH_MISMATCH，自动更新元数据 |

#### 5.2.2 月度校验（每月 1 日 02:00 执行，6 项）

| 校验项 | 校验方法 | 通过标准 | 异常处理 |
|--------|---------|---------|---------|
| 映射冲突检测（多对一） | 检查同一文件关联多个核心表记录，或同一记录关联过多文件（>50） | 冲突数 = 0 | 标记 CONFLICT，通知数据校验员 |
| 元数据完整性检查 | 检查必备元数据字段是否完整（3.1.3 节矩阵） | 完整性 ≥ 95% | 标记 PARTIAL，触发 4.3 元数据提取补全 |
| 关联有效性验证 | 调用 lark-base 验证 related_record_id 是否存在 | 有效率 = 100% | 标记 INVALID_RELATION，删除无效关联 |

```
Step 1: 发现异常

  - 字段：异常ID、类型、级别、文件/节点、发现时间、描述

         ▼

  - P2：周报通知（校验报告中汇总）
  - 动作：collator Agent 调用 lark-im 发送消息
         ▼
Step 4: 修复处理
  - 责任人按级别时效处理
  - collator Agent 辅助执行（自动重命名、补全元数据等）
  - 处理过程记录在异常日志表
         ▼
Step 5: 复核确认
  - 数据校验员复核修复结果
  - collator Agent 自动验证（重新校验异常项）
  - 复核通过 → 进入 Step 6；复核不通过 → 退回 Step 4
         ▼
Step 6: 关闭异常
  - 异常日志表状态更新为 CLOSED
  - 记录关闭时间、关闭人、关闭原因
  - 纳入下次校验报告统计
```

### 9.2 质性收益

1. **知识库检索体验**：通过 7 个一级节点、≤3 层的目标分类树，配合统一数字前缀与索引页设计，用户可在 1 分钟内定位目标 SOP/话术/模板，告别"翻目录"式检索。
2. **collator Agent 数据摄入效率**：通过标准命名规范与 23 项元数据字段，Agent 可自动解析业务ID、建立 STRONG/WEAK 关联，数据摄入耗时从人工辅助降至全自动。
3. **业务资产可追溯性**：通过双向关联（云盘文件链接↔核心表记录），任何一份合同、策划案、成品照片均可追溯到对应客户、订单、拍摄任务，支撑业务复盘与纠纷追溯。
4. **团队协作效率**：通过 RACI 矩阵明确 22 项任务责任分工，配合 5 类自动化工具，重复性工作由 Agent 承担，人工聚焦于内容质量与决策，团队整体效率提升 30%+。

### 9.3 风险与应对

| 风险 | 影响程度 | 发生概率 | 应对措施 |
|------|---------|---------|---------|
| **lark-cli API 限频** | 中（批量操作受阻） | 高 | 所有工具内置限频控制（200-300ms 间隔）+ 指数退避重试 |
| **Tesseract OCR 未安装或准确率低** | 中（工具 4 OCR 功能降级） | 中 | 提供安装指引，降级为仅文件名匹配；可选飞书 OCR API |
| **飞书妙记转写耗时** | 中（工具 4 批量处理慢） | 中 | 异步处理 + 超时控制（30 分钟/文件）+ 失败重试 |
| **云盘 Token 再次失效** | 高（工具 2、5 扫描失败） | 中 | 配置化 Token，支持快速切换；建立 Token 月度验证机制 |
| **命名规则变更** | 低（工具 3、5 规则失效） | 低 | 规则配置化（YAML），无需改代码；规则变更走变更管理流程 |
| **协作管理员补充滞后** | 中（单点维护风险持续） | 中 | M4 里程碑前完成补充；项目负责人跟进 |
| **业务团队抵触新规范** | 中（命名规范执行不到位） | 中 | M4 试点期提供培训 + 工具 3 自动化辅助；M5 推广期纳入考核 |
