## ⚖️ **五大核心约束体系（最高优先级）**

> 以下5大约束是Agent所有执行动作的**最高约束**，任何操作不得违反，违反时必须立即终止并触发告警。

### 约束1：字段约束 🔒
**规则内容**：
- ✅ 所有数据操作**必须严格遵循**步骤1中缓存的7张核心表的**字段结构**
- ❌ **禁止**新增/修改/删除表格字段（除非用户明确要求且经过确认）
- ❌ **禁止**写入不符合字段类型的数据（如向数字字段写入文本）
- ✅ 所有枚举字段的值**必须在预定义的选项范围内**

**违反后果**：立即终止操作 → 输出错误报告 → 建议修正方案

**技术实现**：
```javascript
// 写入前强制校验
function validateFieldWrite(tableName, fieldName, value) {
  const fieldMeta = getCachedFieldMetadata(tableName, fieldName);
  
  // 检查字段是否存在
  if (!fieldMeta) {
    throw new Error(`字段 ${fieldName} 在表 ${tableName} 中不存在`);
  }
  
  // 检查数据类型匹配
  if (!isTypeCompatible(value, fieldMeta.type)) {
    throw new Error(`值 ${value} 与字段 ${fieldName} 的类型 ${fieldMeta.type} 不兼容`);
  }
  
  // 检查枚举值合法性
  if (fieldMeta.type === 'select' || fieldMeta.type === 'multi-select') {
    if (!fieldMeta.options.includes(value)) {
      throw new Error(`值 ${value} 不在字段 ${fieldName} 的允许选项中`);
    }
  }
}
```

### 约束2：操作约束 🛡️
**规则内容**：
- ✅ 任何**写入/修改/删除**表格数据的操作，**必须先执行三重校验**：
  1. **格式校验**: 数据格式是否符合字段要求（手机号11位、日期有效等）
  2. **去重校验**: 是否存在重复记录（相同主键/相同手机号等）
  3. **必填项校验**: 所有必要填字段是否已填写
- ❌ 校验不通过的操作**绝对不得执行**
- ✅ 校验失败时**必须同时触发异常告警**

**三重校验流程**：
```
用户提交数据
    ↓
[1] 格式校验 ──失败──→ 返回格式错误详情 + 正确格式示例
    ↓ 通过
[2] 去重校验 ──发现重复──→ 提示用户选择：更新/跳过/强制创建
    ↓ 通过/已处理
[3] 必填项校验 ──缺失项──→ 列出缺失字段 + 请求补充
    ↓ 全部通过
→ 执行写入操作
```

### 约束3：联动约束 🔗
**规则内容**：
- ✅ 所有数据**成功入库后**，必须**严格执行预设的跨表联动规则**
- ✅ 自动补全关联表格数据，确保**全表数据一致性**
- ❌ 禁止只写单张表而忽略关联表的更新（除非该表确实无关联）

**联动执行清单**（详见后续"跨表联动规则总览"章节）：

| 触发操作 | 必须执行的联动 | 涉及表 |
|---------|--------------|--------|
| 创建客户 | 无直接联动（客户是起始表） | - |
| 创建项目 | 验证客户存在 + 双向关联 | 客户表 ↔ 项目表 |
| 项目分配资源 | 双向关联资源 | 项目表 ↔ 资源表 |
| 项目完成拍摄 | 创建素材记录 + 关联 | 项目表 → 素材表 |
| 项目交付成品 | 创建成品记录 + 关联 | 项目表 ↔ 成品表 |
| 成品引用爆款 | 双向关联爆款 | 成品表 ↔ 爆款库 |

**一致性保障机制**：
```
写入成功 → 触发联动检查
    ↓
扫描关联规则库 → 匹配 applicable rules
    ↓
按序执行联动操作 → 记录每步结果
    ↓
全部成功 → 标记为"一致"
任一失败 → 回滚所有联动 → 报告不一致原因
```

### 约束5：安全约束 🔐（⭐ 新增 - 最高优先级）

**规则内容**（官方明文规定）：

#### 5.1 全量留痕机制
- ✅ **所有操作必须全量留痕**，包括但不限于：
  - 数据读取操作（读取了哪些表、哪些字段、多少条记录）
  - 数据写入操作（写入了什么数据、写到哪个表、写入前后的值）
  - 数据修改操作（修改了哪个记录的哪些字段、旧值和新值）
  - 数据删除操作（删除了哪个记录、删除原因、是否可恢复）
  - 异常操作（什么异常、何时发生、如何处理的）
  
- ✅ **自动写入SOP迭代优化管理表**（Table ID: `tblBApBSUuftxltf`）
  - 每次操作完成后自动生成一条SOP记录
  - 记录内容包含：操作时间、操作类型、操作对象、操作结果、异常信息

**SOP自动记录格式**：
```json
{
  "SOP 名称": "自动化操作日志",
  "适用场景": "Agent自动执行的数据处理操作",
  "当前版本": "V1.0",
  "SOP 状态": "已发布",
  "负责人": "[系统自动]",
  "最近更新内容": "[操作摘要]",
  "更新时间": "[当前时间戳]",
  "备注": "[详细操作记录JSON]"
}
```

#### 5.2 操作追溯能力
- ✅ 支持按以下维度追溯历史操作：
  - **时间维度**: 查询某时间段内的所有操作
  - **表格维度**: 查询某张表的所有变更记录
  - **记录维度**: 查询某条记录的完整修改历史
  - **用户维度**: 查询某个操作者（或Agent）的所有操作
  
- ✅ 每条操作记录应包含足够的上下文信息以便回溯：
  ```json
  {
    "operation_id": "唯一操作ID",
    "timestamp": "ISO8601时间戳",
    "operator": "执行者标识",
    "operation_type": "CREATE/UPDATE/DELETE/BATCH",
    "target_table": "目标表名",
    "target_record_id": "目标记录ID",
    "fields_changed": [
      {"field_name": "字段名", "old_value": "旧值", "new_value": "新值"}
    ],
    "trigger_rules": ["触发的联动规则"],
    "result": "SUCCESS/PARTIAL/FAILED",
    "error_details": "错误详情（如有）",
    "execution_time_ms": "执行耗时"
  }
  ```

#### 5.3 回滚支持
- ✅ 对于关键操作（批量写入、重要数据修改），应具备回滚能力：
  - 在执行前备份受影响的数据快照
  - 如果操作失败或用户要求撤销，可恢复到操作前的状态
  - 回滚操作本身也需记录在案

**回滚流程**：
```
检测到需要回滚的情况
    ↓
查询操作日志获取 operation_id
    ↓
从备份中恢复数据快照
    ↓
验证恢复后的数据完整性
    ↓
记录回滚操作到SOP表
    ↓
通知用户回滚完成
```

#### 5.4 批量删除禁令（硬性规定）
- 🚫 **严禁批量删除核心业务数据**！
  - **定义**: 单次操作影响超过10条记录的删除行为
  - **禁用范围**: 
    - 客户表记录
    - 项目表记录
    - 成品发布表记录
    - 资源总库记录
    - 素材库记录
    - 爆款调研库记录
    
- ✅ **例外情况**（必须满足全部条件才允许）：
  1. 用户**明确主动要求**批量删除
  2. 用户提供了**清晰的目标范围**（如"删除2024年之前的项目记录"）
  3. Agent**二次确认**并展示将被删除的记录清单
  4. 用户**第三次确认**后才执行
  5. 执行前**强制备份**所有将被删除的数据
  6. 执行后**通知用户**删除结果和备份数据位置

**批量删除确认流程**（多重安全门）：
```
用户请求批量删除
    ↓ [第1道门]
Agent识别为批量操作 → 展示将影响的记录数和清单
    ↓ [第2道门]
请求用户第1次确认："确定要删除这N条记录吗？"
    ↓ [第3道门]
用户确认 → 强制执行备份 → 展示备份位置
    ↓ [第4道门]
请求用户第2次（最终）确认："备份已完成，现在执行不可逆删除？"
    ↓ [第5道门]
用户最终确认 → 执行删除 → 记录到SOP → 通知结果
```

#### 5.5 异常告警机制
- ✅ 以下情况必须**立即触发告警**并暂停操作：
  - 权限不足（错误码91403等）
  - 数据冲突（重复主键、逻辑矛盾）
  - 批量操作失败率超过10%
  - 检测到疑似恶意操作（如尝试删除大量数据）
  - API调用异常（连续多次超时、返回非预期结果）
  
- ✅ 告警信息必须包含：
  - 告警级别（🔴严重 / 🟡警告 / 🔵提示）
  - 告警时间
  - 告警原因（详细描述）
  - 影响范围（哪些数据受影响）
  - 建议行动（用户应该做什么）

**告警分级与响应**：
| 级别 | 触发条件 | 响应策略 |
|-----|---------|---------|
| 🔴 严重 | 权限错误、数据丢失风险 | 立即停止所有操作，等待人工介入 |
| 🟡 警告 | 数据冲突、部分失败 | 暂停当前操作，提供解决方案供选择 |
| 🔵 提示 | 非关键性异常、性能下降 | 记录日志，继续执行但降低并发度 |

## 📋 **约束体系总结**

| 约束编号 | 约束名称 | 核心要求 | 优先级 | 违反后果 |
|---------|---------|---------|--------|---------|
| 1 | 字段约束 | 严格遵循表结构，不乱写字段 | P0 | 终止+报错 |
| 2 | 操作约束 | 三重校验通过才执行 | P0 | 终止+告警 |
| 3 | 联动约束 | 入库后自动维护关联 | P0 | 回滚+报告不一致 |
| 4 | 输出约束 | 明确状态+详情+链接 | P1 | 重构输出 |
| **5** | **安全约束** | **留痕+SOP+禁批量删** | **P0** | **终止+告警+追溯** |

**执行原则**: 当多个约束发生冲突时，按优先级排序：**安全 > 字段 > 操作 > 联动 > 输出**

## 跨表联动规则总览

### 核心数据流

```
客户咨询 → 创建客户记录(表1)
    ↓
确认拍摄 → 创建项目记录(表2)，关联客户
    ↓
分配资源 → 更新项目记录，关联资源(表4)
    ↓

    ↓
后期制作 → 更新素材状态，更新项目状态
    ↓
交付成品 → 创建成品发布记录(表3)，关联项目
    ↓
运营发布 → 更新成品发布状态，记录运营数据
```

### 自动化联动清单

| 触发条件 | 自动动作 | 涉及表 |
|---------|---------|--------|
| 创建新客户 | 检查是否有同名/同手机号的重复客户 | 表1 |
| 创建新项目 | 验证客户是否存在，若不存在则提示先创建 | 表1 ↔ 表2 |
| 项目状态变更为"拍摄完成" | 提示创建素材记录 | 表2 → 表5 |
| 项目状态变更为"已交付" | 提示创建成品发布记录 | 表2 → 表3 |
| 创建成品发布记录 | 自动关联所属项目，可选择关联爆款参考 | 表3 ↔ 表2, 表6 |
| 更新成品核心数据 | 自动触发生成Trae数据分析 | 表3 |
| 分配资源给项目 | 双向关联项目和资源 | 表2 ↔ 表4 |

### 一致性保障规则
1. **客户-项目一致性**: 项目的客户姓名必须存在于客户表
2. **项目-成品一致性**: 成品的所属项目必须存在于项目表
3. **项目-素材一致性**: 素材的关联项目必须存在于项目表
4. **状态流转一致性**: 项目状态只能按预定义顺序变更

## 🔗 知识库同步联动规则（V2.0新增）

> **更新日期**: 2026-04-28
> **版本**: V2.0 - 双向同步架构
> **优先级**: 与传统跨表联动规则同级执行

### 核心原则

**表格变化时，自动同步更新对应的知识库页面，确保「数据 ↔ 知识」实时一致。**

### 同步触发矩阵

| 触发操作 | 自动同步动作 | 目标知识库 | 同步方式 |
|---------|-------------|-----------|---------|
| **SOP迭代优化管理表新增优化记录** | 更新对应SOP Wiki页面底部的"最近更新"区域 | SOP迭代优化知识库 | 追加更新日志 |
| **资源总库新增资源记录** | 在资源总库知识库创建/更新对应的资源说明子页面 | 资源总库知识库 | 创建或更新页面 |
| **全场景话术库表新增话术** | 在话术库知识库创建/更新对应的话术条目页面 | 全场景话术库知识库 | 创建或更新页面 |
| **拍摄项目全流程管理表状态变更** | 更新项目案例Wiki页面的进度状态 | 拍摄项目全流程管理知识库 | 追加状态变更记录 |
| **爆款调研库表新增调研记录** | 在爆款调研知识库创建对应的调研分析页面 | 爆款调研库知识库 | 创建新页面 |

### 详细同步规则

#### 规则1：SOP迭代优化 → Wiki页面同步

**触发条件**: `tblBApBSUuftxltf` (SOP迭代优化管理表) 新增或更新记录

**同步流程**:
```
1. 检测到SOP迭代优化管理表有新记录
   ↓
2. 提取关键字段：涉及SOP模块、优化方案、评审状态
   ↓
3. 匹配对应的知识库Wiki页面（通过"涉及SOP模块"字段匹配）
   ↓
4. 在Wiki页面底部追加更新日志块：
   ┌─────────────────────────────────────┐
   │ 📅 [日期] SOP迭代更新               │
   │ • 优化内容：[优化方案摘要]           │
   │ • 评审状态：[已通过/待审核/已驳回]   │
   │ • 记录ID：[recXXXXX]                │
   │ • 查看详情：[多维表格链接]          │
   └─────────────────────────────────────┘
   ↓
5. 记录同步结果到操作日志
```

**示例代码逻辑**:
```javascript
async function syncSopIterationToWiki(record) {
  const sopModule = record.fields['涉及SOP模块'];
  const wikiPageToken = findWikiPageByTitle(sopModule);
  
  if (wikiPageToken) {
    const updateLog = {
      date: new Date().toISOString(),
      content: record.fields['优化方案'],
      status: record.fields['评审状态'],
      recordUrl: `https://pcnafnwqcuzo.feishu.cn/base/MwGMbF0Q0alPc6s3jOccovvOnob/tblBApBSUuftxltf/${record.record_id}`
    };
    
    await larkDoc.appendBlock(wikiPageToken, generateUpdateLogBlock(updateLog));
    logger.info(`SOP迭代已同步到Wiki: ${sopModule}`);
  }
}
```

    │   B. 以表格为准，覆盖Wiki

## 特殊业务场景处理规则

### 场景1：同一客户多次咨询
- **识别方式**: 相同手机号或相同姓名+近似联系方式
- **处理策略**: 
  - 优先更新原有客户记录的"跟进记录"
  - 如果是全新的拍摄需求，创建新项目但关联同一客户
  
### 场景2：批量导入历史数据
- **触发条件**: 用户提供Excel/CSV/多个聊天记录
- **处理策略**:
  - 先解析所有数据，展示预览
  - 请用户确认后再批量写入
  - 批量写入时串行执行，每批≤200条
  
### 场景3：数据冲突检测
- **冲突类型**: 
  - 同一手机号对应不同姓名
  - 同一项目关联了矛盾的资源档期
  - 成品发布时间早于拍摄时间
- **处理策略**: 
  - 立即暂停并报告冲突
  - 提供多个解决方案供用户选择
  - 不擅自做出决定

### 场景4：权限异常恢复
- **异常表现**: 写入失败，返回权限错误码
- **处理策略**:
  - 检查错误码类型（91403等严重错误立即停止）
  - 尝试切换user/bot身份重试一次
  - 若仍失败，输出详细的修复指南

## 数据质量门禁标准

### 必填字段检查（写入前必须满足）
| 目标表 | 必填字段列表 | 阻塞策略 |
|-------|------------|---------|
| 客户表 | 客户姓名、联系方式 | 缺一不可，必须请求补充 |
| 项目表 | 项目名称、客户姓名、项目类型、项目状态、拍摄日期、项目负责人 | 缺一不可 |
| 成品表 | 发布标题、所属平台、发布状态、成品文件 | 缺一不可 |
| 资源表 | 资源名称、联系方式、合作状态 | 缺一不可 |
| 素材表 | 项目名称、素材类型、素材状态 | 缺一不可 |

### 格式验证规则
- **手机号**: 11位数字，不支持座机
- **日期**: 必须可解析为有效日期，不接受"下周"、"月底"等模糊表述（除非能准确推断）
- **URL**: 必须以http://或https://开头
- **金额**: 纯数字或包含"元"等单位符号
- **选项值**: 必须严格匹配枚举值，不支持自定义值（除非字段允许）

### 逻辑一致性检查
- 拍摄日期 ≥ 咨询日期（客户表）
- 项目创建时间 ≤ 拍摄日期
- 成品创建时间 ≥ 拍摄完成时间
- 素材归档时间 ≈ 拍摄时间（允许±1天误差）
