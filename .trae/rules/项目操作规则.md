# collator 项目操作规则

> **适用场景**：在本项目（collator）中进行任何操作时均需遵循
> **优先级**：本规则 `alwaysApply: true`，每次会话自动加载

---

## 🔴 强制规则：进入项目必须先读 Knowledge

**每次新会话开始时**，AI 必须按顺序读取以下知识文件：

| 顺序 | 文件 | 用途 | 智能生效条件 |
|------|------|------|--------------|
| 第1步 | `.trae/Knowledge/项目总览.md` | 了解项目全貌、目录结构、文件映射规则 | **始终必读**（任何操作前） |
| 第2步 | `.trae/Knowledge/业务场景.md` | 理解业务背景、7张核心表、数据架构 | **始终必读**（任何操作前） |
| 第3步 | `.trae/Knowledge/文档集索引.md` | 了解外部文档集资源位置和分类 | 涉及文档查询时 |
| 第4步 | `.trae/Knowledge/飞书API技术要点.md` | 掌握PowerShell/JSON/API调用技术坑点 | **涉及飞书API写入/迁移操作时必读** |
| 第5步 | `.trae/Knowledge/数据摄入实践经验.md` | CSV导入飞书表格的标准化流程与坑点总结 | **涉及CSV/Excel导入、批量数据写入时推荐读取** |

> ⚠️ 未读取以上第1-2步文件前，**不得执行任何项目操作**。
>
> 💡 **智能生效机制说明**：
> - **基础层（第1-2步）**：无条件强制，所有场景都必须先读
> - **上下文层（第3-5步）**：根据用户意图动态加载
>   - 用户提到"文档"、"资料"、"SOP" → 触发读取第3步
>   - 用户提到"写入"、"导入"、"复制"、"迁移"、"同步" + "飞书/表格" → 触发读取第4步
>   - 用户提到"CSV"、"Excel"、"导入数据"、"批量写入"、"场地信息"、"数据摄入" → 触发读取第5步
> - AI应通过关键词匹配自动判断是否需要加载额外Knowledge

## 🟡 条件规则：按场景触发

### 场景A：文件操作（整理/移动/读取/创建）

**触发词**："整理文件"、"这个文件放哪"、"移动文件"、"归档"、"目录结构"、"新建文件"

**必须执行**：
1. 调用 `collator-file-ops` skill
2. 按 skill 中定义的流程执行（扫描→判断→移动/创建→输出摘要）

### 场景B：飞书 API 操作（细分）

**触发词**：任何涉及飞书多维表/文档/云盘/知识库/电子表格的操作

**必须执行**：
1. 先调用 `lark-shared` skill 完成认证检查（新会话/首次使用/遇到失败时）
2. **根据子场景选择对应Skill**：

#### B-1: 电子表格读取/查询
**触发特征**："读取表格"、"查看数据"、"查询"、"获取"
→ 调用 `lark-sheets` skill（+read / +info 命令）

#### B-2: 电子表格写入/修改
**触发特征**："写入"、"更新"、"修改单元格"
→ 调用 `lark-sheets` skill（+write 命令）
⚠️ **注意**：如果遇到JSON解析错误，立即切换到原生API方式

#### B-3: 表格间数据迁移 ⭐
**触发特征**："复制到"、"迁移"、"同步"、"映射"、"从A表复制到B表"、"把...表的数据搬..."
**智能生效条件**（满足任一即触发）：
- 用户明确提到两个不同的表格/工作表
- 包含"复制"、"迁移"、"同步" + "表格"关键词
- 提到"字段映射"、"列对应"、"拆分字段"

**执行流程**（严格按顺序）：
```
Step 1: 读取技术Knowledge（如未读）
   ↓ .trae/Knowledge/飞书API技术要点.md
Step 2: 调用迁移Skill
   ↓ .trae/skills/lark-sheets-migrate/SKILL.md
Step 3: 按Skill流程执行
   ↓ Phase 1: 需求确认 → Phase 2: 数据读取
   ↓ Phase 3: 字段转换 → Phase 4: 批量写入
Step 4: 输出迁移报告
   ↓ 源行数、有效数、成功数、失败详情
```

**关键约束**：
- ✅ 必须先展示字段映射方案，经用户确认后再执行
- ✅ 使用原生API（`lark-cli api PUT`）而非CLI封装命令（避免PowerShell坑）
- ✅ 使用相对路径的临时文件传递JSON数据
- ✅ 分批写入（每批≤50条），输出每批状态
- ❌ 禁止在未确认映射规则的情况下直接写入

#### B-4: 多维表（Base）操作
**触发特征**："多维表"、"记录"、"字段"、"视图"
→ 调用 `lark-base` skill

#### B-5: 文档/知识库/云盘
**触发特征**："文档"、"知识库"、"云空间"、"上传下载"
→ 调用 `lark-doc` / `lark-wiki` / `lark-drive` skill

### 场景C：数据摄入（原始数据→飞书表格）

**触发词**："写入飞书"、"导入数据"、"录入"、"解析这段数据"

**必须执行**：
1. 读取 `docs/guides/data-parsing-templates.md`（解析模板）
2. 读取 `docs/guides/business-rules-library.md`（五重约束校验）
3. 调用 `lark-shared` skill 完成API认证
4. 调用 `lark-base` skill 执行写入
5. 执行跨表联动校验
6. 按约束4（输出约束）格式输出结果

### 场景D：业务咨询（SOP/流程/话术）

**触发词**："模特招募"、"客户咨询流程"、"拍摄执行"、"话术"、"SOP"

**必须执行**：
1. 先查 `docs/sop/` 下是否有对应SOP文件
2. 再查外部文档集 `D:\360Downloads\Trae 项目\文档集\`
3. 最后查飞书知识库（调用 `lark-wiki` skill）

### 场景E：跨窗口协作与 GPT 审计交付（Collator 实施协作包）

**触发词**："Collator_Dify_飞书_Trae实施协作包"、"给 GPT 审计"、"跨窗口实施"、"Phase X"、"阶段报告"、"验收报告"

**必须执行**：
1. 先读取 `docs/Collator_Dify_飞书_Trae实施协作包_v1.0/collator_handoff_v1/Collator_璺ㄧ獥鍙ｅ疄鏂芥墜鍐宊v1.0.md`
2. 读取并持续更新以下状态文件：
   - `docs/PROJECT_STATE.md`：当前阶段、Commit、测试状态、阻塞项、下一步
   - `docs/ACCEPTANCE_REPORT.md`：每条验收命令的日期、环境、退出码、通过/失败数、关键输出
   - `docs/DECISIONS.md`：已锁定架构决策及任何变更提案
3. 每次执行结束按手册格式输出阶段报告，至少包含：
   - 阶段与状态（IN_PROGRESS / BLOCKED / DONE）
   - 当前 Commit Hash
   - 本次完成项与修改文件
   - 实际执行的命令及结果（不得手写未运行的结果）
   - 验收项勾选状态
   - 阻塞项、风险、下一步
4. **不得**以"已完成"、"理论上通过"、"看起来正确"等替代实际运行的测试与审计证据。
5. **不得**伪造 Dify / 飞书真实环境测试结果；外部凭据或环境不可用时标记为 `BLOCKED_EXTERNAL_ENV`。
6. 涉及代码质量时，必须提供 `npm run typecheck`、`npm run lint`、`npm run test`、`npm run test:integration`、`npm run test:coverage`、`npm run build` 等命令的真实输出。

## 🟢 通用规则

### 文件存放规则

```
代码/脚本  → src/
JSON配置   → src/config/
文档/报告  → docs/（guides / reports / sop）
图片/媒体  → public/
AI配置     → .trae/（rules / Knowledge / skills）
```

### 命名规范

- 知识/规则文件：中文描述（如 `项目总览.md`）
- 技能文件：`SKILL.md`（放在技能目录下）
- 配置文件：英文描述 `.json`（如 `batch1.json`）
- 报告文件：`StepN_英文描述_Report.md`

### 操作原则

1. **先读后做**：任何操作前先读取相关 knowledge 和规则
2. **先查后写**：创建文件前检查是否已有类似文件
3. **先确认后执行**：涉及数据写入/文件移动时，先展示计划再执行
4. **操作留痕**：每次重要操作后输出清晰的摘要（成功/失败/影响范围）

## 🔵 Knowledge & Skill 智能加载机制（核心创新）

### 设计理念

本项目采用**三层知识架构**，实现"按需加载、精准匹配"：

```
┌─────────────────────────────────────────────┐
│  Layer 1: 基础知识层（Knowledge）            │
│  ├─ 项目总览.md        → 始终加载           │
│  ├─ 业务场景.md        → 始终加载           │
│  ├─ 文档集索引.md      → 条件加载（文档查询）│
│  └─ 飞书API技术要点.md → 条件加载（API写入） │
├─────────────────────────────────────────────┤
│  Layer 2: 操作技能层（Skills）               │
│  ├─ lark-sheets-migrate  → 表格迁移专用     │
│  ├─ lark-sheets          → 表格读写通用     │
│  ├─ lark-base             → 多维表操作       │
│  └─ ...其他skills                          │
├─────────────────────────────────────────────┤
│  Layer 3: 约束规则层（Rules）               │
│  └─ 本文件（项目操作规则.md）→ 场景触发      │
└─────────────────────────────────────────────┘
```

### 智能生效条件矩阵

| 用户意图关键词 | 触发的Knowledge | 触发的Skill | 优先级 |
|---------------|-----------------|-------------|--------|
| "复制"、"迁移"、"同步" + "表格" | ✅ 飞书API技术要点.md | `lark-sheets-migrate` | P0（最高） |
| "写入"、"导入"、"录入" + "飞书" | ✅ 飞书API技术要点.md | `lark-base` / `lark-sheets` | P0 |
| "读取"、"查看"、"查询" + "表格" | - | `lark-sheets` (+read) | P1 |
| "文档"、"资料"、"SOP" | ✅ 文档集索引.md | - | P1 |
| "整理文件"、"归档"、"目录" | - | `collator-file-ops` | P1 |
| 其他飞书操作 | - | 对应skill | P2 |

### AI决策流程图

```
用户输入
   ↓
[是否包含飞书/表格相关词？]
   ├── YES → [是否涉及数据迁移/复制？]
   │            ├── YES → 加载Knowledge(飞书API)
   │            │         ↓ 调用 lark-sheets-migrate skill
   │            └── NO  → [读/写？]
   │                      ├── 读 → lark-sheets (+read)
   │                      └── 写 → 加载Knowledge(飞书API)
   │                            ↓ lark-sheets (+write) 或原生API
   └── NO  → [是否涉及文件操作？]
              ├── YES → collator-file-ops
              └── NO  → [是否涉及文档查询？]
                        ├── YES → 加载Knowledge(文档集索引)
                        └── NO  → 通用处理
```

### 关键设计原则

#### 1. Knowledge vs Skill 职责分离

| 维度 | Knowledge（知识库） | Skill（技能） |
|------|---------------------|--------------|
| **内容性质** | 通用原理、技术坑点、最佳实践 | 具体操作步骤、代码模板、流程规范 |
| **生命周期** | 相对稳定（更新频率低） | 可随业务变化快速迭代 |
| **示例** | "PowerShell下JSON传递问题及解决方案" | "模特数据迁移的完整Python脚本" |
| **何时读取** | 在调用相关Skill之前 | 匹配到具体场景时 |

#### 2. 避免过度加载

❌ **错误做法**：
```
每次会话开始时读取所有Knowledge和Skill
→ 导致上下文膨胀、响应变慢、token浪费
```

✅ **正确做法**：
```
仅加载基础层（项目总览+业务场景）
根据用户意图动态加载上下文层
→ 精准、高效、节省资源
```

#### 3. 失败回退机制

当Skill执行遇到问题时，按以下顺序回退：

```
1. 检查是否已读取相关Knowledge？
   └─ NO → 先读取Knowledge再重试
   
2. 当前Skill方式是否可行？
   └─ CLI封装命令失败 → 切换到原生API方式
   
3. 是否需要升级处理方案？
   └─ 单条写入失败 → 尝试批量写入
   └─ 批量写入失败 → 减小批次大小重试
   
4. 最终仍失败？
   └─ 输出详细错误日志
   └─ 提示用户手动介入或联系技术支持
```

## 📚 维护指南

### 如何新增Knowledge

1. **识别模式**：当同一技术问题出现≥2次时，提取为通用知识
2. **命名规范**：`{领域}技术要点.md` 或 `{主题}说明.md`
3. **位置**：`.trae/Knowledge/`
4. **更新Rule**：在本文档的"强制规则"表格中添加条目，并定义生效条件

### 如何新增Skill

1. **识别场景**：当某类操作有固定流程且重复出现时，封装为Skill
2. **命名规范**：`lark-{领域}-{功能}/`
3. **位置**：`.trae/skills/`
4. **结构要求**：
   ```
   skill-name/
   └── SKILL.md  （必含：概述、前置依赖、标准流程、错误处理）
   ```

### 如何新增规则

1. **识别触发点**：当AI需要特定引导才能正确执行某类任务时
2. **定义生效条件**：明确的关键词组合或语义特征
3. **指定执行路径**：Knowledge → Skill → 输出格式的完整链路
